# Torus64 Recursive Onion Ring ORAM Implementation Plan

> **For the agent:** Use the `superpowers-executing-plans` skill to implement this plan task-by-task.

**Goal:** Make the recursive Onion Ring ORAM `HomExpand` path paper-faithful by moving the recursive TFHE backend to a 64-bit torus and separating swap-bit and `-s` gadget parameters.

**Architecture:** Keep the current practical packed path safe by default while introducing a Torus64-capable TFHE backend for the recursive path. The ORAM layer should stop assuming one global `TGswParams`; swap-bit controls use `(B=2^3, l=8)`, while the encrypted `-s` helper uses `(B=2^7, l=7)`, sharing the same TLWE/RLWE key over `n=2048`.

**Tech Stack:** C++17, CMake, GoogleTest, TFHE v1.0.1-derived backend, Onion Ring ORAM code under `include/oram/onion_ring` and `src/onion_ring`.

---

## Current Evidence

The existing backend is 32-bit torus based:

- `build/_deps/tfhe-src/src/include/tfhe_core.h:28` defines `typedef int32_t Torus32`.
- `build/_deps/tfhe-src/src/libtfhe/tgsw.cpp:17-18` computes gadget scales with `1 << (32 - (i + 1) * Bgbit)`.
- `src/onion_ring/HomExpand.cpp:96-97` rejects recursive key-switch decompositions above 31 bits.
- `src/onion_ring/PermGen.cpp:104-113` correctly packs recursive rows independently at `h[row] / N`; do not change this algorithm.

The row-specific tests already added in `test/onion_ring/homexpand_test.cpp` show the failure happens before the final RLWE-to-RGSW lift:

- `RecursiveExpandRlweKeepsOneHotCoefficientIndicesAcrossRows` fails at `row=1 hot=0` with many false positives.
- `RecursiveExpandRlweIsolatesGateBitsAcrossRowsInOrder` fails at row 1 and row 2, with row 2 corrupted across non-origin coefficients.

**Step 1: Add a torus bit-width constant**

In `tfhe_core.h`, introduce:

```cpp
constexpr int TFHE_TORUS_BITS = 64;
typedef int64_t Torus64;
typedef Torus64 Torus32;  // temporary API compatibility shim
```

Why keep `Torus32` temporarily: it minimizes ORAM-side churn while the backend is migrated. After tests pass, optionally rename ORAM-facing helpers to avoid semantic confusion.

**Step 2: Replace hard-coded `32` decomposition widths**

In backend code, replace expressions like:

```cpp
1 << (32 - ...)
uint32_t
int32_t prec_offset
modSwitchToTorus32
modSwitchFromTorus32
tGswTorus32PolynomialDecompH
```

with 64-bit-safe equivalents:

```cpp
Torus32(1) << (TFHE_TORUS_BITS - ...)
uint64_t
int64_t prec_offset
```

Keep function names initially if changing them would cause unnecessary call-site churn, but change their internals to 64-bit semantics.

**Step 3: Fix unsigned decomposition buffers**

In `tgsw-functions.cpp`, update decomposition internals from `uint32_t* buf` and `uint32_t maskMod/offset` to `uint64_t* buf` and `uint64_t maskMod/offset`.

Expected critical locations:

- `tGswTorus32PolynomialDecompH`
- `Torus32PolynomialDecompH_old`
- any AVX2-specific code path that assumes 32-bit lanes

If AVX2 paths are 32-bit-specific, disable them for the Torus64 backend first. Correctness comes before vectorized speed.

**Step 4: Fix gadget scale construction**

In `tgsw.cpp`, change:

```cpp
int kk = (32 - (i + 1) * Bgbit);
h[i] = 1 << kk;
```

to:

```cpp
int kk = (TFHE_TORUS_BITS - (i + 1) * Bgbit);
h[i] = Torus32(1) << kk;
```

Expected with `N=2048, Bgbit=3, l=8`: every `h[row] / N` is non-zero, and row 7 starts at `2^29`.

**Step 5: Fix serialization**

In `tfhe_io.cpp`, ensure every torus coefficient read/write uses `sizeof(Torus32)` after the typedef has widened. Add version metadata only if backwards compatibility with existing serialized 32-bit ciphertexts is required.

For this migration, it is acceptable to invalidate previous serialized expansion bundles and ciphertexts.

**Step 6: Fix Gaussian/noise generation**

Audit `gaussian32`, `dtot32`, `t32tod`, and all torus conversion helpers in `numeric-functions.cpp`.

Expected behavior:

- `modSwitchToTorus32(1, 8)` represents `1/8` over `2^64`.
- `modSwitchFromTorus32(modSwitchToTorus32(x, M), M) == x` for relevant `M`.
- Gaussian samples are scaled to the 64-bit torus.

             source,

## Known Risks

- TFHE v1.0.1 has many hard-coded 32-bit assumptions. Missing one will usually show up as broken gadget decomposition or serialization.
- FFT paths may assume 32-bit integer lanes. Disable vectorized paths first if correctness is unclear.
- Existing serialized ciphertexts and bundles should be considered incompatible after the Torus64 migration.
- The recursive path will likely be much slower and memory-heavier with `n=2048,l=8`.
- Keeping function names like `modSwitchToTorus32` while widening semantics is acceptable as an intermediate step only; document or rename later to avoid future confusion.
