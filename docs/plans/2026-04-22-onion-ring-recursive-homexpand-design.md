# Onion Ring Recursive HomExpand Design

## Goal

Add the paper-faithful recursive RLWE coefficient-expansion optimization from Onion Ring ORAM
while keeping the currently verified practical packed path available as an oracle and fallback
during development.

## Current Baseline

The branch already contains:

- real TFHE integration through `FetchContent`,
- runtime-configurable Onion Ring parameters,
- RAII wrappers for TLWE/TGSW ciphertexts and serialized expansion-bundle scaffolding,
- a working Onion Ring client/server protocol over `NetIO`,
- a tested Waksman permutation layer,
- a practical packed transport path that batches encrypted gate controls into fewer transport
  frames,
- end-to-end tests that cover eviction, leaf refresh, and a long-horizon rewrite regression.

That practical path is now the trusted oracle for the next phase. It proves the protocol and
server-side permutation flow are working, but it is not the paper's coefficient-packed RLWE
transport. The remaining gap is the recursive `expandRlwe` + `homExpand` path that reduces
client-to-server swap-control traffic to a small number of RLWE ciphertexts instead of sending
full per-gate controls.

## Design Choice

Use a coexistence architecture until the recursive path is fully verified:

- keep the current practical packed path intact as the default live path,
- add a second paper-faithful recursive transport/expansion mode beside it,
- compare both modes on the same permutations and ciphertext traces,
- switch the live default only after the recursive mode passes the end-to-end suite.

This keeps the strongest available test oracle in the repository while the most fragile
cryptographic logic is being developed.

## Architecture

### 1. Two Packed Backends, One Protocol Surface

`OnionRingClient` and `OnionRingServer` should keep the same high-level eviction and refresh
flow. The change belongs behind a transport-mode boundary:

- the current practical mode continues batching already-formed `RGSWCiphertext`s,
- the new recursive mode sends a paper-style packed RLWE payload plus the expansion bundle,
- both modes terminate at the same `WaksmanNetwork::EvalWaksman()` call.

This keeps bucket routing, access scheduling, and network command structure stable while the
transport format and unpacking math evolve underneath.

### 2. `PermGen` Owns Transport-Mode-Specific Payload Construction

`PermGen` should provide two distinct packed payload constructors:

- `BuildPracticalPackedSwapBitPayload(...)` for the current verified batching path,
- `BuildRecursivePackedSwapBitPayload(...)` for the paper-faithful coefficient-packed path.

The recursive payload must actually encode many gate bits inside RLWE coefficients rather than
serializing already-lifted controls. This is the critical difference between the oracle path and
the target path.

### 3. `HomExpand` Splits Into Two Layers

The recursive server-side path should be explicit in code:

1. `ExpandPackedRlwe(...)`
   - input: packed RLWE payload,
   - output: a gate-ordered vector of isolated RLWE ciphertexts,
   - mechanism: recursive `Subs` plus key-switch support material.

2. `LiftExpandedRlweToRgsw(...)`
   - input: isolated RLWE ciphertexts,
   - output: the final per-gate `RGSWCiphertext` controls,
   - mechanism: paper-style external-product lift using `A = RGSW(-s)`.

The public `HomExpandPackedSwapBits(...)` entry point should dispatch by payload mode and call
either the current practical unpacker or the recursive expansion + lift pipeline.

## Cryptographic Data Flow

### Client Setup Bundle

The recursive path needs server-side support material generated by the client at initialization:

- substitution support keys for each recursive level,
- RLWE/LWE key-switch material used after substitution,
- the paper-specific lift support ciphertext `A = RGSW(-s)`,
- enough metadata to reconstruct the bundle for the active runtime parameters.

The current expansion bundle scaffolding already carries these pieces conceptually. The recursive
follow-up should make the contents real and mode-specific instead of placeholder-compatible.

### Recursive Access-Time Payload

For each triplet eviction or leaf refresh in recursive mode:

- compute the target permutation with the existing Waksman network,
- derive the gate-bit sequence,
- pack many gate bits into a small number of RLWE ciphertexts by coefficient position,
- send those packed RLWE ciphertexts instead of batched per-gate TGSW ciphertext blobs.

### Server-Side Expansion

For each recursive payload:

- deserialize packed RLWE ciphertexts,
- run recursive coefficient isolation with `Subs` and key-switch support,
- preserve gate ordering exactly,
- lift isolated RLWE bits into `RGSWCiphertext` controls,
- feed those controls into the existing `EvalWaksman()` boundary.

The server still never decrypts.

## Components

### `TFHEAdapter`

`TFHEAdapter` will need to support the real recursive bundle:

- real key-switch material for recursive expansion,
- reliable serialization/deserialization of that material,
- support helpers for `RGSW(-s)` and any substitution-key families needed by `Subs`.

### `PermGen`

`PermGen` will need:

- a transport-mode enum or equivalent dispatch surface,
- recursive RLWE coefficient-packing helpers,
- serialization for recursive packed payloads,
- preservation of the current practical batching path as the oracle backend.

### `HomOps`

`HomOps::Subs()` and related helpers become part of the critical path for correctness.
They need to be exercised directly in recursive-path tests rather than remaining thin wrappers
that are only validated indirectly.

### `HomExpand`

`HomExpand` becomes the main implementation target:

- recursive expansion helpers,
- RLWE isolation ordering guarantees,
- external-product lift,
- comparisons against the practical packed oracle,
- dispatch between practical and recursive modes.

### `OnionRingClient` and `OnionRingServer`

Protocol updates should remain minimal:

- add a transport-mode configuration switch,
- keep practical mode as the live default until recursive mode is proven,
- allow end-to-end tests to instantiate either mode,
- keep server request handlers structurally identical beyond the unpacker dispatch.

## Error Handling

The recursive path should fail loudly when:

- payload mode and serialized data do not match,
- packed RLWE payload sizes do not align with runtime parameters,
- expansion-bundle contents are missing or malformed,
- recursive isolation returns the wrong gate count,
- recursive and practical control counts diverge in comparison tests.

No silent fallback should happen inside production code. Tests may intentionally run both modes,
but runtime dispatch should be explicit.

## Testing Strategy

### 1. Unit Tests for Recursive Packing and Isolation

Add focused tests that verify:

- recursive packed payloads contain fewer ciphertexts than per-gate controls,
- recursive expansion preserves gate order,
- isolated RLWE outputs decrypt to the same bits as the practical oracle on small permutations.

### 2. Lift Comparison Tests

Add tests that verify:

- recursive RLWE-to-RGSW lift yields the same logical control bits as the practical oracle,
- recursive and practical controls drive identical Waksman outputs on the same encrypted blocks.

### 3. Dual-Mode End-to-End Tests

Run Onion Ring end-to-end tests in both transport modes:

- practical mode remains the baseline,
- recursive mode is the candidate,
- both must preserve eviction and leaf-refresh correctness.

### 4. Long-Horizon Regression

Keep a rewrite-heavy regression for recursive mode, but scale it for faster iteration:

- use `10 * a` rather than `300 * a`,
- use a smaller block size than the current long-run practical-path stress test,
- keep the existing larger practical-path stress test as the stronger baseline until cutover.

This gives the recursive mode a realistic stability test without making every TDD loop too slow.

## Success Criteria

This follow-up is complete when:

- the recursive path uses real coefficient-packed RLWE payloads,
- the recursive unpacker matches the practical packed oracle on control bits and Waksman outputs,
- the Onion Ring end-to-end suite passes in recursive mode,
- a scaled long-horizon recursive regression passes with repeated rewrites,
- the codebase is ready to switch the live default from practical mode to recursive mode.
